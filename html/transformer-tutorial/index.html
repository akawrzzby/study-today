Transformer 基础与 TRACE AS STATE 图解

回答三个问题：① 自回归生成是什么？② 因果注意力为什么"不能回头改"？③ KV cache 是什么？以及——既然第一遍已经得到答案，论文为什么还要推理第二遍？
① 自回归生成 ② 因果注意力 ③ KV cache ④ 论文的两遍流程 ⑤ 为什么还要第二遍

0一句话总览

论文 TRACE AS STATE 不改 Transformer 的架构、不训练模型，只改输入的组织方式：让模型先读一遍长上下文并"打草稿"（第一遍推理），再把草稿（推理痕迹 T）放到上下文最前面，让模型重读一遍（第二遍推理）。因为 Transformer 是因果的——每个位置只能看到它前面的内容——把 T 放最前面，等于让所有"早期位置"都能看到后期才确定的"任务状态"。

动手玩：下面 4 个模块都可以点按交互。第 1–3 节补 Transformer 基础，第 4–5 节回到论文本身。

1自回归生成（Autoregressive Decoding）

"LLM 是一个一个往外吐 token" —— 这句话的准确含义：模型每一步只预测下一个 token，预测完把它接到输入末尾，再预测下一个。生成的每一步，模型的输入就是"已经生成的全部内容"。

P(y) = P(y₁) · P(y₂ | y₁) · P(y₃ | y₁,y₂) · …

试一试：点击"生成下一个"

关键点：每一步生成时，模型"看到"的是 全部历史 token（当前行里亮色的部分）。这就是你说的"每次输出之前都会把之前的输出重新输入进去"——注意，它能看到的是过去，永远看不到未来。

2因果注意力："所有位置一起做 attention" 是什么意思

训练和"预填充"时，整段输入是一次性全部喂给模型的——所以叫"所有位置一起做 attention"。但每个位置能"看"谁是受限制的：位置 i 只能看 1…i，这就是因果掩码（causal mask）。

点击下方任意 token，看它能"看到"谁

直觉：整段一起算 ≠ 每段都能看全段。位置 i 的隐藏表示 hᵢ 只由 c₁…cᵢ 决定（hᵢ = f(c₁,…,cᵢ)）。一旦算完，hᵢ 就定稿了——后面位置的信息无论多重要，都进不了 hᵢ。这就是"不能回头改"的数学来源。
和破案例子的对应：读卷宗时，第 30 页的"解读"= h₃₀，只用了前 30 页的信息；第 500 页揭示凶手 = c₅₀₀，它改不了 h₃₀。要改，只能"重读一遍"（新的 pass），让第 30 页重新计算——这就是第二遍推理做的事。

3KV cache：生成时为什么不是每步重算

生成第 6 个 token 时，它要 attend 到前面 5 个 token。问题：前面 5 个位置的 Key / Value 每次都要重新算吗？

无缓存（naive）：每步重算全部前缀

c₁c₂c₃c₄c₅→c₆

生成 c₆ 时，c₁…c₅ 的 K/V 全部重算一遍。生成长度 n 时总开销 O(n²)，又慢又浪费。

有 KV cache：只算新 token，复用旧的

c₁c₂c₃c₄c₅→c₆

c₁…c₅ 的 K/V 存在缓存里（绿色），c₆ 只算自己的 Q/K/V，再与缓存做 attention。每步开销 O(n)，总开销 O(n)。

关键点（和论文的关系）：KV cache 复用的是已经定稿的旧表示。缓存不会"吸收"后面的新信息去更新旧位置——旧位置的 K/V 就是它被处理那一刻的值。所以 cache 只是省计算，不改变因果性。想让早期位置看到新信息，唯一办法是重跑一遍包含新前缀的前向（附录 F 的 token 用量表就是这套重跑的实际成本）。

4TRACE AS STATE 怎么对 Transformer 做工作

不改架构、不改权重、不训练——只改变第二遍推理时输入的组织方式。

第一遍（Pass 1）：读上下文 + 打草稿

x（长上下文）→ M（模型）→ r（推理痕迹） a（可见答案）→ π（序列化器）→ T（痕迹块）
第一遍只做推理（reasoning only），把中间思考 r 打包成固定格式的 T

第二遍（Pass 2）：同一个模型、同一份上下文，只有 T 的位置不同

T→ x→ M→ r′ a′ TRACE AS STATE [T, x] ✔
x→ T→ M→ r′ a′ TRACE APPEND [x, T]
为什么 [T, x] 有效：第二遍重读时，x 的每一个位置（包括最早期）的前缀里都多了 T。注意力视角下，早期位置这次能 attend 到任务状态了——等于把"条件在后"（坏情况，为所有可能状态留残差映射）改成了"条件在前"（好情况，只跟一条状态路径）。
为什么 [x, T] 是合格对照：T 在最后，早期位置照样看不到它，救不了已经定稿的表示——所以 TRACE APPEND 只是"换一种输入顺序"的参照物。

5为什么还要第二遍？第一遍不是已经有答案了吗？

第一遍确实有答案——但那个答案是在"不知道任务状态"的情况下盲答的，准确率很低。第二遍的目的不是"再算一遍"，而是带着已确定的状态重读上下文，得到更准的答案。

第一遍（盲答）

29.2%
GraphWalks Parents 精确匹配（DeepSeek V4 Pro）。早期位置被迫对所有可能状态"留一手"，表示模糊，答案自然差。

TRACE APPEND（草稿放最后）

43.0%
草稿 T 只在最后一段可被使用，救不了前面已经定稿的表示——只有小幅提升。

TRACE AS STATE（草稿放最前）

81.8%
重读时每个位置都能看到状态，表示清晰，答案大幅提升。27 个组合里 26 个优于 TRACE APPEND。

那"成本"呢？—— 注意：不是省钱，是加钱买准确率

纠正一个常见误解：TRACE AS STATE 并没有减少计算开销。它多跑了一遍完整推理，而且第二遍输入更长（多了 T），token 用量反而增加（附录 F：TRACE AS STATE 的总输入 token ≈ 第一遍 + 第二遍）。它真正减少的是概念上的"残差映射负担"——早期位置不再需要同时维护 k 套可能状态的解读。代价是翻倍的推理成本，收益是大幅提升的准确率（如 29.2% → 81.8%）。
一句话：第一遍 = 打草稿（把状态"外化"成文本 T）；第二遍 = 带着草稿重读、重新作答。两遍用的答案可以完全不同——第二遍才是论文报告成绩的那一次。
